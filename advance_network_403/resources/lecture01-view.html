Slide 9

TCP vs UDP: two transport contracts

EXPLAINED

The transport layer offers applications a service contract. TCP promises that every byte you write will arrive, exactly once and in order, or that you will be told the connection failed. To keep that promise it needs a connection (state at both ends), sequence numbers, acknowledgments and retransmissions.
UDP promises almost nothing: each datagram is sent independently and may be lost, duplicated or reordered. In exchange it adds only 8 bytes of header and no set-up delay, which suits short exchanges (DNS) and real-time media where a late packet is as useless as a lost one.
An important subtlety is that TCP is a byte stream: if you send two 100-byte messages, the receiver may read 200 bytes at once or 50 bytes at a time. Applications must define their own message boundaries.

EXAMPLE

A video call uses UDP (RTP): if a voice packet is lost, retransmitting it 100 ms later is pointless. A file download uses TCP: a single missing byte would corrupt the file.

REMEMBER

TCP = reliable ordered byte stream with flow and congestion control. UDP = best-effort datagrams. QUIC rebuilds TCP-like reliability on top of UDP.

Slide 11

TCP header: field by field

EXPLAINED

Each TCP segment carries a header of 20 bytes plus up to 40 bytes of options. The port numbers identify the two application processes; together with the two IP addresses they form the 4-tuple that names a connection.
The sequence number is the position (in bytes) of the first data byte of this segment in the sender’s stream. The acknowledgment number tells the other side “I have received everything up to this byte; send me this one next”. Because it is cumulative, one ACK can confirm many segments.
The flags control the connection: SYN opens it, FIN closes it gracefully, RST aborts it, ACK means the acknowledgment field is valid, PSH asks the receiver to deliver data to the application promptly. The window field is how the receiver says how much more data it can accept — this is the heart of flow control.

EXAMPLE

A segment with seq = 5001 carrying 1000 bytes contains bytes 5001–6000. The receiver answers with ack = 6001, meaning “next I expect byte 6001”.

REMEMBER

Sequence and ACK numbers count bytes, not packets. The ACK number is always the next byte expected.

TCP options that matter for performance

M

MSS

Maximum Segment Size, announced in the SYN. Typically 1460 bytes on Ethernet (1500 MTU − 40). Avoids IP fragmentation.

W

Window Scale

Shift count (0–14) applied to the 16-bit window, allowing windows up to 1 GiB. Negotiated only in SYN/SYN-ACK (RFC 7323).

S

SACK

Selective Acknowledgment: receiver reports non-contiguous blocks received, so the sender retransmits only the holes (RFC 2018).

T

Timestamps

TSval/TSecr enable accurate RTT measurement on every ACK and PAWS protection against wrapped sequence numbers (RFC 7323).

12

Slide 13

TCP options that matter for performance

EXPLAINED

The original TCP header was designed in 1981 for slow links. Options extend it without changing the fixed header. Four options are negotiated in almost every modern connection, and they are only valid if both SYN and SYN-ACK carry them.
MSS tells the peer the largest segment you can receive, avoiding IP fragmentation. Window Scale multiplies the 16-bit window field by 2^shift so the window can exceed 64 KB — essential on fast, long paths. SACK lets the receiver report which out-of-order blocks it already has, so only the missing pieces are resent. Timestamps echo a clock value so the sender can measure RTT on every ACK and detect wrapped sequence numbers on very fast links.

EXAMPLE

A firewall that strips the Window Scale option silently limits every connection through it to 64 KB in flight. On a 100 ms path that caps throughput at about 5 Mb/s even on a 1 Gb/s link.

REMEMBER

Options are agreed in the handshake and fixed for the whole connection. Check them first when diagnosing slow transfers.

Slide 16

Three-way handshake and option negotiation

EXPLAINED

Before any data flows, both sides must agree on starting sequence numbers and options. The client sends a SYN with its initial sequence number x and its options. The server replies with SYN-ACK: its own initial sequence number y, an acknowledgment of x+1 and its options. The client completes with an ACK of y+1.
Why three messages and not two? Each side must prove it received the other’s sequence number. Two messages would leave the server unsure that its SYN reached the client. Initial sequence numbers are random so an attacker cannot guess them and so that segments from an old connection are not mistaken for new ones.
Handshake state is a target for attacks: a SYN flood sends many SYNs without completing them, filling the server’s queue. SYN cookies encode the state inside the server’s ISN so nothing must be stored until the final ACK arrives.

EXAMPLE

Client SYN seq=1000, server SYN-ACK seq=5000 ack=1001, client ACK seq=1001 ack=5001. The first data byte from the client will be numbered 1001.

REMEMBER

The handshake costs one RTT before data can be sent. Later lectures (TLS 1.3, QUIC) work hard to reduce this cost.

Slide 18

Connection teardown and TIME_WAIT

EXPLAINED

TCP is full-duplex, so each direction is closed separately. The side that finishes first (the active closer) sends FIN; the other side acknowledges it but may continue sending its own data (a half-close). When it is done, it sends its own FIN, which the active closer acknowledges.
After that last ACK the active closer waits in TIME_WAIT for twice the Maximum Segment Lifetime. This serves two purposes: if the final ACK was lost, the peer will resend its FIN and we can answer it; and any delayed duplicate segments from this connection will expire before the same 4-tuple can be reused.
RST is different: it aborts the connection immediately and discards any data still in buffers. It is sent, for example, when a segment arrives for a port with no listening application.

EXAMPLE

A load-testing client opening thousands of short connections per second can run out of local ports because each closed connection keeps its port in TIME_WAIT for 60 seconds (Linux).

REMEMBER

Whoever closes first holds TIME_WAIT. Servers usually prefer clients to close first.

19

Slide 20

The TCP state machine in five phases

EXPLAINED

TCP defines eleven states, but they group naturally into five phases. A server starts in LISTEN; a client moves from CLOSED to SYN_SENT when it calls connect(). During the handshake the server is in SYN_RECEIVED. When the handshake completes, both reach ESTABLISHED, where all data transfer happens.
Closing involves several intermediate states depending on who closes first and whether both close at the same time: FIN_WAIT_1 and FIN_WAIT_2 for the active closer, CLOSE_WAIT and LAST_ACK for the passive closer, and the rare CLOSING state for simultaneous close. Finally the active side spends time in TIME_WAIT before returning to CLOSED.
Knowing these states is practical: a server with thousands of sockets in CLOSE_WAIT usually means the application is not calling close() — an application bug, not a network problem.

EXAMPLE

Command: ss -tan state close-wait lists connections the remote side has closed but your application has not yet closed.

REMEMBER

ESTABLISHED = data phase. Many CLOSE_WAIT = app bug. Many TIME_WAIT = many short connections from this host.

22

Slide 23

Sliding-window flow control

EXPLAINED

The receiver stores incoming data in a buffer until the application reads it. If the sender transmitted faster than the application reads, this buffer would overflow and data would be lost. Flow control prevents that: in every segment the receiver advertises rwnd, the free space left in its buffer.
The sender may have at most rwnd bytes “in flight” (sent but not yet acknowledged). As acknowledgments arrive the left edge of the window moves forward; as the application reads data the receiver advertises more space and the right edge moves forward. The window therefore slides along the byte stream.
Because the sender must wait for ACKs, at most one window of data can be delivered per round-trip time. This gives the fundamental limit: Throughput ≤ Window / RTT. The faster or longer the path, the bigger the window must be.

EXAMPLE

With rwnd = 64 KB and RTT = 100 ms: 65 535 × 8 bits / 0.1 s ≈ 5.2 Mb/s. Doubling the window to 128 KB doubles the maximum throughput to about 10.5 Mb/s.

REMEMBER

The sender obeys min(rwnd, cwnd). rwnd protects the receiver; cwnd (Lecture 2) protects the network.

24

Slide 25

Sender’s view of the byte stream

EXPLAINED

Picture the sender’s data as a long line of numbered bytes divided into four regions. On the far left are bytes already sent and acknowledged: the sender can free that buffer space. Next come bytes sent but not yet acknowledged: they must be kept in case they need retransmitting.
Then comes the usable window: bytes the sender is allowed to send right now without waiting. Everything to the right is outside the window and must wait. The window size equals the in-flight bytes plus the usable bytes.
When an ACK arrives, the boundary between the first two regions moves right and the usable window grows. If the receiver advertises a smaller window, the right edge stops moving; if it advertises zero, the sender stops completely and starts the persist timer.

EXAMPLE

Window = 10 000 bytes, 6 000 in flight ⇒ 4 000 usable. An ACK for 3 000 bytes arrives with the same window ⇒ 3 000 in flight and 7 000 usable.

REMEMBER

Window = in flight + usable. ACKs move the left edge; window advertisements move the right edge.

26

Slide 27

Bandwidth-Delay Product (BDP)

EXPLAINED

The bandwidth-delay product is the amount of data that fits “in the pipe” between sender and receiver: link capacity multiplied by round-trip time. To keep a link busy, the sender must have at least one BDP of data in flight at all times; otherwise it will sit idle waiting for ACKs.
The BDP grows with both speed and distance. A 10 Mb/s link with a 20 ms RTT has a BDP of only 25 KB, but a 1 Gb/s link across a continent (80 ms) has a BDP of 10 MB — more than 150 times the maximum unscaled TCP window.
This is why window scaling exists and why operating systems auto-tune socket buffers. If either the sender’s send buffer or the receiver’s receive buffer is smaller than the BDP, throughput will be limited no matter how much capacity the network has. Such paths are called long fat networks (LFNs).

EXAMPLE

1 Gb/s × 0.08 s = 80 000 000 bits = 10 MB. Needed window-scale shift: 10 MB / 64 KB ≈ 153 ⇒ shift of 8 (×256).

REMEMBER

BDP = capacity × RTT. Buffers and windows must be at least the BDP to fill the link.

28

Slide 29

Zero window and the persist timer

EXPLAINED

If the receiving application stops reading (it is busy, blocked or slow), the receive buffer fills up and the receiver advertises rwnd = 0. The sender must then stop sending data entirely.
There is a danger here: when the application finally reads data, the receiver sends a window update. That update is a pure ACK with no data, and TCP never retransmits pure ACKs. If it is lost, the sender waits for a window that never comes and the receiver waits for data that never comes — a deadlock.
To prevent this the sender starts a persist timer and periodically sends a tiny zero-window probe. The receiver must answer each probe with its current window, so the sender eventually learns that space is available. The probe interval grows exponentially to avoid wasting bandwidth.

EXAMPLE

In Wireshark you will see “TCP ZeroWindow” from the receiver, then “TCP ZeroWindowProbe” from the sender every 0.2, 0.4, 0.8 s…, followed by “TCP Window Update” when the application reads again.

REMEMBER

Zero windows point to a slow receiving application, not to network congestion.

Slide 30

Silly Window Syndrome and its cures

1

The problem

Tiny windows or tiny writes cause many segments carrying a few bytes each, with a 40-byte header — wasting bandwidth and CPU.

2

Receiver fix (Clark)

Do not advertise a small window increase; wait until the window is ≥ 1 MSS or half the buffer.

3

Sender fix (Nagle)

If unacknowledged data is outstanding, buffer small writes until a full MSS accumulates or an ACK arrives.

4

Nagle + delayed ACK

Combined they can add ~40–200 ms stalls for request/response traffic. Interactive apps set TCP_NODELAY.

30

Slide 31

Silly Window Syndrome and its cures

EXPLAINED

Silly Window Syndrome happens when TCP ends up sending lots of tiny segments. On the receiver side, an application that reads one byte at a time causes the receiver to advertise a one-byte window; on the sender side, an application that writes one byte at a time causes one-byte segments. Each carries 40 bytes of headers, so efficiency collapses.
Clark’s rule fixes the receiver side: do not advertise a window increase until it is at least one MSS or half the buffer. Nagle’s algorithm fixes the sender side: while any data is unacknowledged, collect small writes into one segment instead of sending each immediately.
Nagle interacts badly with delayed ACKs (receivers wait up to 40–200 ms hoping to piggy-back the ACK on data). A request split into two small writes can then stall until the delayed ACK fires. Latency-sensitive applications (SSH, games, RPC) disable Nagle with the TCP_NODELAY socket option.

EXAMPLE

Typing in an SSH session sends one keystroke per segment — a 41-byte packet carrying 1 byte of data. With Nagle, keystrokes typed during one RTT are combined into one segment.

REMEMBER

Small writes + Nagle + delayed ACK = mysterious 40–200 ms delays. TCP_NODELAY is the usual fix.

Slide 33

Observing flow control on Linux

EXPLAINED

Linux exposes the internal state of every TCP connection. The command ss -tin prints, for each socket, the negotiated window scale (wscale), the current congestion window (cwnd), the smoothed RTT (rtt), and how much receive space the kernel has allocated (rcv_space).
The tcp_rmem and tcp_wmem settings contain three values: minimum, default and maximum buffer size. The kernel automatically grows buffers between default and maximum as a connection needs them (auto-tuning). If the maximum is smaller than the BDP of your path, auto-tuning cannot help — that is when administrators raise net.core.rmem_max and the third tcp_rmem value.
Wireshark adds its own analysis on top of a capture: filters such as tcp.analysis.zero_window or tcp.analysis.window_full find flow-control problems instantly, even in captures with millions of packets.

EXAMPLE

ss -tin output: “wscale:7,7 rtt:48.2/3.1 cwnd:120 rcv_space:262144” ⇒ scaling ×128 both ways, 48 ms RTT, 120 segments in the congestion window, 256 KB receive space.

REMEMBER

Measure before tuning: ss for socket state, sysctl for buffer limits, Wireshark for evidence.

Slide 36

Model answers

A1

Because TCP is a byte stream: segment boundaries can change on retransmission, but byte positions never do. The ACK number is the next byte the receiver expects; everything before it has arrived.

A2

MSS, Window Scale and SACK-permitted (and Timestamps, which must start in the SYN). If a middlebox strips them, the connection falls back: no scaling (64 KB max window), no SACK, default MSS — often a large performance loss.

A3

TIME_WAIT lets the active closer re-send the last ACK if the peer’s FIN is retransmitted, and ensures old duplicates of this connection expire (2×MSL = maximum lifetime in both directions) before the 4-tuple is reused.

A4

5 Mb/s ≈ 64 KB / 100 ms, so the transfer is window-limited: window scaling is missing or the receive buffer is too small. Fix: enable window scaling end-to-end and raise socket buffer maxima to ≥ BDP (12.5 MB).

Key takeaways

TCP provides a reliable, ordered, full-duplex byte stream with flow and congestion control

Handshake options (MSS, Window Scale, SACK, Timestamps) shape performance for the whole connection

Flow control limits the sender to the receiver’s advertised window; throughput ≤ window / RTT

High-BDP paths need window scaling and large socket buffers

Zero windows and silly-window effects are usually end-host problems, not network problems
